# Architecture and implementation boundaries

## 1 October 2026 — Trial workspace and task navigation

Authenticated `/workspace` dispatches active managed learners to their separate protected home; verifies adults; preserves platform-admin precedence; derives school destinations from current staff tenant access and family access from active verified GuardianLinks. One eligible school or family destination redirects directly, while several show an authorized chooser. No active institutional access falls back to `/study`. Adult-only `/dashboard` remains compatible and shares dispatch; explicit personal study and each protected target retain their own middleware/policy checks. No remembered default or role-granting chooser is introduced.

School home/task queries reuse current memberships, teacher assignments, active schools/classes, recipient/enrolment and released-review boundaries. Read services provide bounded summaries without fetching authored response text for counts. Guardians receive recent linked-child attendance and sent notices; learner feedback remains separate and release-restricted. No unread tracking is implied.

Learning retains its existing transactional services and schema, organized into focused task views. Named links carry only validated numeric locators and view mode; course → assignment → response is resolved under the authorized tenant. Ordinary navigation supplies refresh/history, and saved editors are hydrated from the server. Livewire updates recheck access. Browser draft warnings protect navigation; server finality/publication checks remain authoritative. See the [implementation plan](plans/school-trial-usability.md) for scope/evidence.

Updated 26 September 2026. School administration plus non-AI e-learning is the accepted product direction. The school architecture below remains a proposed implementation design except for the implemented SP0 AI job boundary, SP1 access/lifecycle slices, SP2 records, SP3-01 through SP3-04 slices, SP4-01/02 fee and receipt slices, and SP4-03 charge-credit, allocation-reversal, and manual refund slices recorded below. Cash-refund behavioral verification remains pending. P1–P5 provide existing individual-user/internal-alpha foundations. The earlier AI-oriented design remains below as historical context and deferred work.

### Tenancy and user relationships

Start with one PostgreSQL database and explicit `school_id` ownership for school records. This is a design selection for the bounded pilot, not a claim that isolation is already implemented. A request chooses only a school for which the actor holds an effective membership; submitted IDs never establish membership. Policies authorize the action and class/learner scope. Parent relationships are separately verified, with access limited to the linked child and released information. Global role fields do not replace school roles.

Use scoped nested route binding where appropriate, explicit policy authorization, same-school relational checks and database constraints. Carry school/actor identifiers into jobs explicitly; recheck mutable access before sensitive delivery/export and clear contextual state between jobs. Scope private objects, export downloads, caches and reports. A missing tenant is an error for school operations, never permission to query all schools. No global school-admin or platform-admin bypass for private content. Support access is justified, time-limited and audited.

The first SP1 slice now implements additive `schools`, `school_memberships`, `school_role_assignments`, and `audit_events` tables plus an atomic provisioning service. Provisioning requires a verified global platform administrator and a verified first school administrator; it assigns only the scoped `school_admin` role and records the actor/event. Invitations, context selection, revocation, and route-level isolation are not implemented yet.

The SP1 context slice implements EnsureSchoolContext for the protected school overview. Route model binding identifies a candidate school, then the middleware rechecks active school status and the authenticated user's active membership on every request. Unauthorized, removed, and inactive contexts return 404; the authorized membership is attached only to the current request. SchoolPolicy::view now repeats the active-school/membership decision at the controller boundary. Navigation lists only active memberships in active schools; a durable selected-school preference and nested resource policies remain open.

Invitation and role lifecycle services now hash one-use invitation tokens, bind them to existing verified users, recheck expiry/revocation/assignment during acceptance, and audit each mutation. Staff roles are limited to scoped school roles; they cannot change `UserRole`. Role and membership removal reject the last active school administrator. Validated Blade flows now expose invitation review/acceptance, revocation, role assignment/removal, and membership removal. Email delivery remains separate work; the current acceptance link is intentionally a local/demo session flash.

The first SP2 registry slice implements `learner_profiles` and school-scoped `enrolments`. Admission is an audited transaction, admission numbers are unique per school, active staff can view the registry, and only school administrators can admit learners. Nested route binding and an enrolment policy prevent cross-school reads. A second SP2 slice implements verified `guardian_links`: school administrators link existing verified users to enrolments, guardians see only active linked learners, and revocation is audited and immediately enforced. Classes/terms, imports, transfers, and learner login remain later SP2 work.

The third SP2 slice implements school-scoped `academic_years` and `terms`. Staff can view the calendar, administrators create years and terms, date ranges are validated, overlapping terms are rejected within an academic year, and mutations are audited. At that slice boundary, classes, subjects, teaching assignments, imports, transfers, and learner login remained later SP2 work; the subsequent class, subject, and teaching-assignment slices are now implemented.

The fourth SP2 slice implements school-scoped `class_groups` and `subjects`. Class groups belong to an academic year, subject codes are unique within a school, staff can view both, administrators create them, and creation is audited. The fifth SP2 slice implements school-scoped `teaching_assignments`: administrators assign active school teachers to same-school class groups and subjects, staff can view assignments, duplicate combinations are rejected, and creation is audited. The sixth SP2 slice implements private staged learner imports: school administrators upload a fixed CSV shape, review per-row validation, commit valid rows, and receive audited checksum-based replay protection. The seventh SP2 slice implements dated learner class memberships: administrators create same-school placements with effective dates, staff can view history, overlapping placements are rejected under an enrolment lock, and creation is audited. The eighth SP2 slice implements promotion, dual-school-admin transfers, and deactivation without deleting source history; managed learner login is blocked after deactivation and lifecycle actions are audited. Authorized exports remain later SP2 work.

The first SP3 slice implements school-scoped attendance sessions and entries. A session belongs to one active class, teaching assignment, and local session date; entries are materialized for learners whose dated class placement covers that date. `unmarked` is stored separately from attendance outcomes, retries update the same logical session, and a version check rejects stale saves. Assigned teachers and school administrators can operate only within their school/class boundary. Attendance corrections, guardian attendance views, notices, and delivery were separate follow-up slices; the first three are now implemented below.

The second SP3 slice implements immutable attendance correction history. Changing an existing entry status requires a reason, records the prior/new status, actor, timestamp, and session version in `attendance_entry_corrections`, and commits with the versioned register update. Missing reasons and stale versions leave both the current entry and correction history unchanged. Alert confirmation/suppression is not implemented yet.

The third SP3 slice extends the existing guardian portal with a selected linked child and read-only attendance history. The controller re-resolves active guardian links, active schools, and active enrolments from the authenticated guardian on every request; an unknown or revoked child selection returns 404. Attendance queries are constrained by both the selected relationship and school, preventing sibling and cross-school leakage.

The first SP3-04 notices slice adds school-admin drafts and sends targeted to all active guardians or the active guardians of a current class placement. Sending resolves recipients in a transaction, writes an idempotent `message_deliveries` ledger for the in-app channel, marks the announcement sent, and records a school audit event. The guardian portal reads only delivered rows belonging to the authenticated guardian. Email/SMS providers, retries, and read/acknowledged state remain deferred.

SP4-01 adds school-admin fee schedules and charge batches. Schedules can be scoped to an open term and/or active class; posting requires a saved preview hash/time and rechecks the eligible active enrolments and schedule snapshot before writing immutable posted charges under an idempotent school/schedule/batch key. Stale previews must be refreshed, and currency values display as major units while storage and calculation use integer minor units. Preview and posting lock the school row before the schedule row. Admission, import commit, class placement, promotion, withdrawal, and transfer take the same school lock before changing fields used by eligibility, so posting sees a stable roster snapshot. A PostgreSQL concurrency test confirms that posting waits for an in-flight admission and then rejects its stale preview without writing charges. SP4-02 adds manually confirmed school receipts and allocations in a separate ledger. Receipt recording and allocation serialize on a locked school row; allocation also locks the receipt and posted charge, rechecks both remaining balances, and records an audit event in the same transaction. A receipt may be split across sibling charges, but an allocation cannot exceed either the receipt's available balance or the charge's outstanding amount; leftover funds remain unallocated credit. A PostgreSQL race test confirms one allocation wins when concurrent requests compete for one receipt balance. The tenant Filament fee page now provides native schedule creation, preview/confirmed posting, receipt recording and allocation actions, all using the same transactional services as the canonical fee routes; the canonical page remains available for full history. SP4-03 adds idempotent charge-credit requests with a separate active school-admin reviewer, full-allocation reversal by an active school admin, and a separate school-refund ledger. Refund requests require a second active school administrator; approval reserves unallocated receipt funds, rejection releases them, and a separate manual payout-completion action records the actor and method/reference. School and receipt locks serialize refund reservations with allocations and reversals. Refund entries and audit transitions are append-only; receipts, allocations, reversals, and charges are not edited, and a refund does not reduce the learner's charge. The additive migration passed on an isolated Docker PostgreSQL database; behavioral and race verification and synthetic browser acceptance remain pending. Live provider verification, opening balances, statements, reconciliation, and residence-specific rules remain open; school tuition remains separate from Nova revenue.

SP4-04 school statement and reconciliation access remains school-admin-only per owner decision. Statement rows derive from posted charges, approved credits, verified receipt allocations, and allocation reversals; refunds and unallocated sibling receipt amounts do not appear on an individual learner statement. The guardian endpoint checks the authenticated user's active verified relationship and the single enrolment on every request, including CSV exports. The internal reconciliation page reports charge-side and receipt-side differences without changing ledger records. No statement tables or external settlement integration are introduced.

The authenticated UI treats active school workspaces as the primary destination: eligible school staff enter the Filament tenant directly after authentication, while only independent-study and guardian users render the personal dashboard. The Breeze shell contains personal tools and the separate guardian portal; school operations are not duplicated there. The public landing page describes the accepted school administration and e-learning direction and does not present deferred AI or unimplemented school workflows as available.

The dashboard and shared navigation target the Filament platform/school panels where slices exist, while attendance and communications remain linked to their canonical scoped routes until panel parity is verified. The school panel has an explicit tenant home page at `/school/{tenant}` that renders the school overview directly. This prevents login from depending on the fallback tenant redirect before reaching a valid page and keeps `/school/{tenant}/school-overview` available as the named overview route.

The FI-03 platform slice adds a Filament school directory and provisioning page. The directory exposes school metadata and membership counts, not learner or finance records. ### Non-AI publication and learning

Keep legacy personal documents/chats private. New classroom resources use an explicit publishing boundary and licence/school scope. Lessons move draft → reviewed/publishable → published → withdrawn. SP5-02 assignments are saved as drafts against a published lesson version; publication freezes the assignment fields and atomically snapshots active learners with dated placements in the assigned class. Later enrolments do not inherit an existing assignment. Withdrawing the source lesson withdraws dependent assignments. The SP5-03 text slice lets a recipient save one draft and submit once with a durable acknowledgement reference. Submission after the due time is marked late only through the configured cutoff; without a cutoff, the due time is final. Final submissions are immutable in this first slice. The SP5 review slice adds one school-scoped review per final submission. Assigned teachers and authorized school administrators can read final responses, save private feedback with an optional integer score/maximum, and explicitly release it. Save/release services use the supplied actor for policy authorization and lock the school, assignment, submission and review in the existing order. Release is idempotent and records one audit event; released feedback is immutable. Learner reads eager-load only their own released review, with matching school scope; draft feedback is never sent to learner views. No review means awaiting review; score zero is a marked result. This is classroom feedback rather than formal assessment/report publication. Attachments, resubmission history, teacher extensions, rubric marking and feedback amendments remain later SP5 work. An ungraded response is not zero. Independent catalogue questions can have automatic fixed-key marking; school open-response marking belongs to authorized teachers.

School report records are distinct from learning practice attempts. Only an authorized academic publication step creates a released report snapshot. Corrections generate a reviewed new version; changes to teaching content or rubrics cannot silently rewrite past reports. No provider call, embedding or document text extraction is needed for any of these paths.

SP0 now has a server-side AI boundary for explicit school and managed-learner execution contexts, including the existing generation jobs. The default configuration denies provider dispatch, marks blocked work failed, and releases a pending usage reservation; personal/internal-alpha jobs remain deliberately retained. Merely hiding navigation is insufficient, and future school routes must pass an explicit context after SP1 authorization exists. Preserve existing records and do not erase AI code or dependencies as part of the pivot.

### Three financial domains and entitlement evaluation

School software invoices and independent learning purchases fund Nova access grants. School tuition/boarding charges and receipts fund school receivable accounts. Keep their ledgers, merchant references and reports separate even when they share a provider adapter. Store money as integer minor units/currency. Verify a payment's recipient/merchant, amount, reference and state before using it; provider initiation is not settlement.

Use transactions, row locks and unique logical keys for receipt allocation, posted charge batches, subscription grants and final submissions. Make external verification outside short database locks and reconcile uncertain results. Durable callback/event receipt precedes background processing; dispatch downstream notices after commit. Refunds, reversals and credits are explicit linked operations rather than destructive edits. Manual recording must name its authorized actor and verification source.

Authorization precedes commercial entitlement: first check actor/learner/resource relationships, then select an effective school or personal grant for the resource. School-assigned work uses school cover and cannot consume a private AI allowance or require a separate personal subscription. Independent subscriptions grant only the licensed catalogue. School onboarding must expose overlapping personal cover and apply an agreed transition policy. Expiry/grace/export behavior must be represented explicitly, not inferred from a single `subscription_status` field.

### Files, jobs and infrastructure

Private file upload validation/scanning is independent of AI ingestion. SP5-01 application code stores uploads on the private local disk under opaque quarantine keys, validates type/content and size, then calls private ClamAV `clamd` before a resource can be published. Scanner outage leaves files pending and unavailable; fail closed. Local `CLAMAV_SOCKET` is unset and host placement, signature updates, monitoring and recovery still require validation. Authorized download requests resolve lesson/version/resource ownership and recheck current school membership, learner placement or teacher assignment and publication state; no public or reusable object URL substitutes for authorization. Accepted limits are 10 MB per file, 500 retained resources and 2 GiB per school, with an 80% warning. A withdrawn/deleted resource becomes inaccessible immediately; after 90 days, purge bytes but retain required history metadata. These classroom files are never sent through Tika, vector, or AI services.

Use PostgreSQL for transactional constraints, existing queue/cache abstractions and private storage. Introduce Redis/shared locks and S3-compatible production storage only with configuration and driver verification; do not claim local Compose services prove deployment readiness. Separate payment/notifications/import queues so a roster import cannot delay callbacks. Make important jobs idempotent; align execution timeout and reservation timeout. Existing vector/Tika components can remain for legacy development but are not on the school release's critical path.

The proposed backup/restore, import cutover, support and boarding fallback obligations are defined in [verification and operations](verification-and-operations.md). Deployment target and service contract remain undecided. No cloud resources or migrations were provisioned during planning.

Framework primitives were checked against installed Laravel 13 documentation: [scoped route binding](https://github.com/laravel/docs/blob/13.x/routing.md), [pessimistic locking](https://github.com/laravel/docs/blob/13.x/queries.md), [jobs after commit](https://github.com/laravel/docs/blob/13.x/queues.md). Use the relevant project skills and version-specific documentation again when implementing APIs not covered by this research.

## Storage and authentication

Propose PostgreSQL as selected by the SAD, with a vector extension such as pgvector subject to host support and a retrieval benchmark. Store embeddings per chunk with model/version and dimensions; changing models requires a deliberate reindex. Use Redis for cache, queues, and locks; private S3-compatible storage for uploads; and an external email provider.

For the first-party Blade/Livewire web app, P1 implements session authentication with CSRF protection, Laravel's password-reset and email-verification flows, and verified middleware on the student dashboard. The SAD's Sanctum requirement is reserved for a future API/mobile use case unless an actual token-authentication need emerges. P1 profile images are stored on the private local disk and returned only from an authenticated endpoint for the current account. Never expose long-lived provider credentials to browsers.

## Document processing and grounded answers

1. Authorize upload and reserve storage allowance; validate declared and detected format/size, then store privately with a generated key.
2. Dispatch processing after persistence commits. Track uploaded → validating → extracting → embedding → ready, with failed/deleting alternatives.
3. Scan and extract in resource-limited workers. Reject malformed archives, encrypted/unreadable files and unsafe paths. Report scanned/image-only files as requiring OCR when text cannot be extracted.
4. Normalize and chunk extracted text, preserving page/section location. Embed bounded batches with retry ceilings. Mark ready only when the expected chunks are durable.
5. At question time, authorize the conversation and selected document IDs, filter candidates by owner and ready state, and retrieve bounded relevant chunks. Build context within a token budget.
6. Generate an answer with citations to stored chunk locations. If evidence is insufficient, say so; distinguish general tutoring from document-grounded responses.
7. On deletion, tombstone the document immediately, prevent new retrieval and late jobs, then remove objects/chunks/embeddings/caches. Explain backup retention separately from immediate product deletion.

Uploaded instructions are untrusted source material. They cannot override system instructions, invoke tools, or widen retrieval scope. Render user/AI content with escaping or a safe Markdown pipeline. Keep private response caches scoped to user, source versions, and model configuration; do not share answers across students by question text alone.

## AI execution and cost controls

P2 supplies the local accounting boundary before any provider integration: an active subscription period and active plan feature are required to reserve finite usage. Each reservation uses a unique logical request key, and settlement produces one usage record. Database row locks protect the normal per-period reservation path; verify its behavior under the production PostgreSQL/Redis deployment before using it for chargeable traffic. P2 intentionally provides no provider adapter, plan seed, or commercial access grant.

Persist a pending message/generation and reserve quota before dispatch. Use queued processing and status polling for the first implementation; evaluate streaming separately. Measure submission-to-complete latency including queue wait. Provider errors should produce retryable user-visible states without creating duplicate completed generations.

Bound tokens, conversation history, question/card counts, extraction pages/time, embedding batches, and retries. Record provider request IDs and actual token usage where supplied. Retrying an uncertain external request can incur another charge; distinguish internal job idempotency from provider billing guarantees. Reconcile stale reservations and alert on spend spikes. Select concrete models, SDKs, dimensions, retention settings, and pricing only after current provider documentation and an evaluation in P0/P4.

## Payment processing

Create a local order and pending attempt with a server-calculated price snapshot before calling Daraja. Persist provider references and return a pending state to the student. A successful initiation or browser redirect is not evidence of payment.

Receive callbacks durably, validate format, correlate to the expected attempt, and apply the provider-supported authenticity/verification controls confirmed during the integration spike. Do not assume a callback signature is available. Resolve uncertain results through supported status queries/reconciliation and manual review where necessary.

After verified success, lock the billing records and atomically record the unique receipt plus entitlement period. Duplicate notifications must be harmless; amount/account mismatches must enter review. Handle pending → succeeded/failed/cancelled/expired, with late or contradictory results routed through reconciliation. Repeated renewals must not overwrite or double-extend a period. Notify the customer after commit. Schedule checks for stale pending payments and expose them to administrators.

## Deployment and scaling

Start with the SAD's Ubuntu/Nginx/PHP-FPM environment or an equivalent managed host, PostgreSQL, Redis, object storage, supervised workers, and one scheduler. Confirm resource sizing through load tests. Keep document, AI, and notification work in separate queues so large extraction jobs cannot starve tutoring or payment handling. Ensure webhook receipt remains responsive.

Scale stateless web instances and queue workers independently, centralize sessions/cache, index ownership/date queries, and tune retrieval before adding infrastructure. Add load balancing and database capacity as metrics justify them. The 100,000-user target is a capacity-planning goal, not a reason to introduce microservices initially.
